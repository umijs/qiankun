# 什么是微前端

微前端(Micro-Frontends)是把后端微服务那套思路搬到前端：一个大型的前端应用，拆成若干个能独立开发、独立部署的小应用，再在运行时组合成一个完整的产品。

这个词最早出现在 2016 年的 ThoughtWorks 技术雷达里。核心诉求很朴素——当一个前端项目大到一个团队扛不动的时候，得有办法把它拆开。

## 为什么会需要它

大部分前端项目一开始都是一个仓库、一套技术栈、一个团队，这样最省事。问题都是长出来的：

- 代码库越滚越大，新人要花很久才能摸清全貌，一次改动的影响范围也越来越难评估。
- 参与的人多了，大家挤在同一条发布链上，谁想上线都得排队、都怕带崩别人。
- 技术栈被钉死在了立项那天。三年前选的框架，今天想换，却发现牵一发而动全身。
- 有时候还得跟历史包袱共存——一个 AngularJS 的老系统，想一点点换成 React，但没法停下来重写。

这些都不是纯技术问题，更多是**组织和协作**的问题。微前端给出的答案是：按团队、按业务把应用拆成互相独立的部分，让每一块都能自己说了算。

## 它的几个基本主张

不同的微前端方案实现差别很大，但大体认同这么几条：

- **独立开发、独立部署。** 每个微应用有自己的仓库、自己的构建、自己的发布节奏。改一个应用不需要重新构建、重新发布其他应用。
- **技术栈无关。** 主应用不该限制微应用用什么框架。React、Vue、Angular 甚至纯 HTML 能同时存在，新应用也不必迁就老应用的选型。
- **运行时集成，而不是构建时集成。** 各个应用是在浏览器里被组装到一起的，而不是在打包阶段被塞进同一个 bundle。这样才谈得上独立部署。
- **相互隔离。** 一个应用的样式、全局变量、运行时错误，不应该影响到另一个应用。这是"多个应用共处一页"能成立的前提。

## 它不是万能的

微前端解决的是**规模**带来的问题，代价是引入了额外的复杂度：一套加载和隔离的运行时、跨应用的通信约定、多份重复的依赖。

所以如果你的应用一个团队就能舒服地维护、一套技术栈也够用，那大概率不需要微前端——普通的路由加代码分割更简单。当应用的边界开始对应到**团队边界和部署边界**，拆分的收益才真正大过它的成本。

## qiankun 在其中的位置

微前端只是一种架构思路，落地需要一套具体的运行时。[qiankun](/zh-CN/guide/what-is-qiankun) 就是这样一套框架：它负责把每个微应用从各自的 HTML 入口加载进来，给它一份隔离的运行环境，在合适的时机挂载和卸载。至于每个微应用内部用什么框架、怎么构建，qiankun 一概不管。

如果你之前考虑过用 iframe 来做隔离，建议先读一读[为什么不是 iframe](/zh-CN/guide/why-not-iframe)——那是很多人踩过的一个坑。
