# 为什么不是 iframe

聊到"在一个页面里隔离多个应用"，几乎所有人第一反应都是 iframe。它天然就有最彻底的隔离——独立的 `window`、独立的 `document`、独立的样式和脚本环境，子应用怎么折腾都出不来。

如果 iframe 真够用，qiankun 就没必要存在了。问题在于，iframe 那份"彻底的隔离"同时也是它最大的麻烦：隔得太死，反而让"多个应用像一个产品"这件事做不顺。具体有四个绕不过去的坑。

## 1. URL 状态不同步

iframe 内部的路由跳转，不会反映到浏览器地址栏上。于是：

- 用户刷新页面，iframe 会回到它的初始地址，子应用里的当前位置丢了。
- 浏览器的前进 / 后退按钮管不到 iframe 内部的历史。
- 想把某个子应用的具体页面分享给别人？地址栏里根本没有那个信息。

要把 iframe 的路由和主应用的地址栏手动同步起来，是能做，但相当别扭，而且很容易出边界情况。

## 2. UI 出不了 iframe 的边界

iframe 是一个硬边界，里面的内容再也越不出去。这在做交互时很致命：

- 一个本该在整个页面居中的弹窗、遮罩，只能在 iframe 这个小框里居中。
- 子应用里的下拉菜单、提示气泡，一旦超出 iframe 的可视区域就会被裁掉。

结果就是，你得为这些跨边界的 UI 场景专门想办法，而它们在普通页面里本来根本不是问题。

## 3. 加载慢，还容易白屏

每加载一个 iframe，浏览器都要重新建一整套上下文，把里面的资源重新下载、解析、执行一遍。哪怕主应用和子应用共用同一批依赖，也没法复用。切换应用时用户经常先看到一段白屏，体验谈不上顺滑。

## 4. 隔离过头，通信反而变难

iframe 把 `document` 也切开了，主应用和子应用活在两个割裂的 DOM 树里。这带来一堆本不必要的成本：

- 跨 iframe 通信只能靠 `postMessage`，连传个对象都得序列化，同步调用更是别想。
- Cookie、`localStorage` 这些，跨 iframe 想共享要额外费一番功夫。
- 事件也被框住了——外层点一下想让 iframe 里的浮层关掉，这种再普通不过的联动都得特意处理。

## qiankun 怎么做

qiankun 的思路是：该隔离的地方隔离，不该隔离的地方保持通畅。

微应用**不**装进 iframe，而是直接挂载到主应用页面的一个容器元素里，和主应用共用同一个 `document`。这样一来，上面那些由"`document` 被切开"引发的问题——URL 不同步、UI 越不出边界、通信困难——从根上就不存在了。

那隔离靠什么？靠运行时：

- **[JS 沙箱](/zh-CN/concepts/js-sandbox)**用一层 `Proxy` 隔离膜，给每个微应用一份独立的 `window` 视图。全局变量的读写、定时器、事件监听都被记账，卸载时逐一还原，应用之间不会互相污染。
- **[样式隔离](/zh-CN/concepts/style-isolation)**基于原生 CSS `@scope`，按需开启，把微应用的样式限定在它自己的容器里，而不需要 iframe 或 Shadow DOM 那种硬边界。

于是你既拿到了应用之间该有的隔离，又没丢掉"它们本来就在同一个页面上"带来的所有便利。这就是 qiankun 不用 iframe 的原因。
