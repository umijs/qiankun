# JavaScript 隔离

qiankun 让多个微应用运行在同一个页面中，但不会让每个应用都不受约束地占用主应用的全局对象。JavaScript 隔离默认开启：每个应用会看到一份自己的 `window` 视图，同时仍能使用普通 Web 应用依赖的浏览器 API。

它的目标是减少可信应用之间的意外干扰，而不是安全地运行不可信代码。

## 心智模型

每个微应用都有一份虚拟全局对象，应用里的 `window`、`self` 和 `globalThis` 都指向这份视图。

| 操作 | 用户可观察的结果 |
| --- | --- |
| 写入 `window.feature = value` | 值属于当前应用，不会发布到主应用或兄弟应用。 |
| 读取应用自己设置的全局变量 | 返回当前应用自己的值。 |
| 读取应用没有设置的全局变量 | 查找可以穿透到主应用，因此标准浏览器 API 和主应用提供的全局对象仍然可用。 |

这种不对称是有意的：写入被隔离，读取则尽量保持与所在页面兼容。同一个微应用的两个实例也会获得彼此独立的全局视图。

## qiankun 会隔离和追踪什么

应用自己的全局变量会留在虚拟对象上，不会修改主应用。除此之外，qiankun 还会追踪一些通过沙箱浏览器视图产生的常见副作用，包括：

- 仍在运行的 interval，以及注册在沙箱 `window` 上的事件监听；
- 与 history 相关的监听；
- 属于应用的动态 script、style 和 stylesheet link。

这些只是常见的托管副作用，并不代表每一种浏览器 API 都会被拦截。

执行 `unmount` 时，qiankun 会移除它能够追踪的副作用，并停用当前应用的全局视图。应用自己的全局变量仍保持隔离，并可在之后重新挂载时复用；它们不会发布给兄弟应用。

应用或应用实例不再使用时，一定要调用 `unmount`。跳过卸载，也会跳过与该实例绑定的清理工作。

## 微应用仍需负责什么

沙箱清理不是通用的资源管理器。qiankun 无法推断应用代码或第三方库创建的每个对象应该活多久。

微应用仍应在 `unmount` 中主动释放自己的资源，尤其是：

- 框架根实例、router、store 和订阅；
- 应当停止的 `WebSocket`、`EventSource`、Worker 和进行中的请求；
- `MutationObserver`、`ResizeObserver` 和 `IntersectionObserver`；
- 主动注册到应用容器之外的回调或 DOM 节点。

显式清理也能让应用独立运行、重新挂载和多实例运行时保持一致。

::: tip
把自动清理当作安全网，而不是用它替代边界清晰的 `unmount` 实现。
:::

## 责任边界

- **它不是安全沙箱。** 应用共享页面的 JavaScript 执行环境，并能读取没有被自身遮蔽的主应用全局变量；只应运行可信代码。
- **只有经过沙箱视图的操作才能被追踪。** 通过沙箱之外的对象创建的资源仍由应用负责。
- **主应用仍能影响微应用。** 对共享浏览器服务或主应用对象的直接修改，不会因为某个微应用卸载而回滚。
- **隔离不会创建私有后端或存储。** Cookie、Storage、网络服务等设施仍遵循浏览器原本的同源共享语义。

## 配置与下一步

`sandbox` 默认是 `true`。设为 `sandbox: false` 后，应用会直接共享真实全局对象，qiankun 的原生 ESM 隔离路径也会一并关闭。它应当只是兼容性逃生口，而不是性能开关。

选项定义见 [AppConfiguration](/zh-CN/api/configuration)，清理时机见[微应用生命周期与 props](/zh-CN/concepts/lifecycle-and-props)，模块应用见[原生 ESM 支持](/zh-CN/concepts/esm-sandbox)。维护者可以继续阅读 [JS 沙箱实现](/zh-CN/internals/js-sandbox)。
